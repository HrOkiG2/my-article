「単一テーブルの更新なら、トランザクションはいらないのでは?」という意見を、バックエンドエンジニアの視点で整理しました。
DBのトランザクションを、どこまで使うか迷っている方に向けた内容です。

## 結論

* **単純なUPDATE 1発**なら、トランザクションは必須ではありません。ただし、将来の拡張を考えて、貼っておくと安心です。
* **読んでから書く(SELECT + UPDATE)**なら、ロックを維持するために、**絶対に必須**です。単一テーブルでも同じです。
* **複数テーブル**の更新なら、**絶対に必須**です。

## 単一テーブルの単純な更新: 同僚が正しかった?

同僚との雑談で、「単一テーブルの更新なら、わざわざトランザクションを貼らなくてもよくない?」という一言が出ました。

```sql
UPDATE users SET name = 'Tanaka' WHERE id = 1;
```

正直に言うと、**データの物理的な整合性(ACID特性)という点では、同僚の言うとおり、トランザクションは必須ではありません。**
MySQLやPostgreSQLなどの現代のRDBMSは、この1行のSQLが実行されるとき、内部で自動的にトランザクションのような処理を行い、次のことを保証してくれます。

* データ行の書き換え
* インデックス(B-Treeなど)の更新
* 一意制約などのチェック

これらは「成功するか、失敗するか」のどちらかで、「データは書き換わったのに、インデックスが壊れた」ということは起きません。

### それでもトランザクションの枠を作る理由

私が、それでもトランザクションを貼ることが多いのは、**未来のバグを防ぐため(防御的プログラミング)**です。

いまは「名前の変更だけ」かもしれません。
でも、半年後に、「名前変更の履歴も、ログテーブルに残して」と仕様が変わったらどうでしょう。
トランザクションの枠(`DB::transaction` など)がないコードだと、改修する人が、履歴保存の処理を、うっかり追加するだけで、トランザクション漏れが起きるリスクがあります。

最初から「更新処理のまとまり」として定義しておけば、処理が増えても安全です。
「転ばぬ先の杖」として、設計の意図をコードに残す意味でも、価値があると思います。

## SELECTが絡むとき: 最大の落とし穴

「単一テーブルだから大丈夫」と油断して、一番痛い目を見るのが、**Read-Modify-Write(読んで、加工して、書く)**のパターンです。
たとえば、銀行口座や在庫の管理で、「今の値を取得して、計算して、更新する」処理です。

1. **SELECT**: 現在の残高を取得します(例: 1,000円)。
2. **アプリ側**: 500円を引く計算をします(1,000 - 500 = 500)。
3. **UPDATE**: 残高を500円で更新します。

これを安全に行うには、読み取る時点で、排他ロック(`SELECT ... FOR UPDATE`)が必要です。

### トランザクションがないと、ロックは機能しない

ここで重要なのが、**「ロックの寿命は、トランザクションの終わりまで」**というルールです。
明示的にトランザクションを貼らずに、`FOR UPDATE` を投げても、Auto Commitが働いて、即座にロックが解除されてしまいます。

```sql
-- トランザクションなしの場合
-- ① ロック付きで読む……つもりだが
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
-- ★ ここでAuto Commitが働いて、即座にトランザクション終了 & ロック解除!
-- (この計算処理中に、他の処理が割り込めてしまう)

-- ② 更新
UPDATE accounts SET balance = 500 WHERE id = 1;
```

トランザクションの枠がないと、せっかくのロックが一瞬で外れて、**競合(Race Condition)**によるデータ不整合を防げません。
単一テーブルでも、**ロジックを含んだ更新をするなら、トランザクションは必須**です。

Laravelでの例です。

```php
use Illuminate\Support\Facades\DB;
use App\Models\User;

DB::transaction(function () use ($userId) {
    // ▼ ここでロック
    $user = User::lockForUpdate()->find($userId);

    // この時点で、レコードはロックされています。
    // 他のトランザクションが、この行を lockForUpdate しようとすると、
    // ここで待機状態になります。

    $user->balance = $user->balance - 500;
    $user->save();
}, 3); // デッドロック対策(リトライ回数)
```

## 複数テーブルの更新: 言わずもがなの大本命

複数テーブルにまたがる更新は、「必須」と言って反対する人はいないでしょう。

* `users` テーブルに、ユーザーを作成します。
* `profiles` テーブルに、初期プロフィールを作成します。

トランザクションがないと、「ユーザーは作れたけれど、プロフィール作成でエラーが出た」という状態で処理が終わってしまい、**プロフィールを持たない、不完全なユーザー**がDBに残ります。
これを防ぐのが、トランザクションの**「All or Nothing(全部やるか、全部やらないか)」**という原則です。

## トランザクションは「お守り」ではなく「シートベルト」

「単一テーブルならトランザクションはいらない」という意見は、単純な値のセットにおいては、技術的に正解です。
ただし、バックエンドエンジニアとしては、次のスタンスがよいのではないでしょうか。

1. **単純な更新(UPDATE 1発)**なら、必須ではないが、将来の拡張性を考えて貼っておくと安心です。
2. **読んでから書く(SELECT + UPDATE)**なら、ロックを維持するために**絶対に必須**です。
3. **複数テーブル**なら、**絶対に必須**です。

DBはアプリケーションの心臓部です。「たかが単一テーブル」と侮らずに、適切なロックとともに、トランザクションを貼っていきましょう。

## まとめ

* 単純な1行のUPDATEは、DBが原子性を保証してくれます。
* Read-Modify-Writeでは、トランザクションとロックがセットで必要です。
* 複数テーブルの更新には、必ずトランザクションを使いましょう。
