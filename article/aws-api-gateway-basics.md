AWS API Gatewayを、ただのルーターだと思っていた私が、調べて分かったことをまとめました。
API Gatewayの役割や、REST APIとHTTP APIの違いを知りたい方に向けた内容です。

## 結論

API Gatewayは、ルーティングだけでなく、**認証・認可、キャッシュ、スロットリング、データ変換**まで担う、マネージドな玄関口です。
バックエンドの前段で、認証やトラフィック制御をまとめて任せられます。

## はじめに知っておくこと

API(Application Programming Interface)は、**リクエストを投げるためのインターフェース**です。
テレビのリモコンを思い浮かべてください。
ボタンを押すと、特定の動作が実行されます。リモコン内部の詳細な処理は、知らなくても大丈夫です。
APIも同じで、呼び出し側は、必要な情報を渡すと、求めるデータが返ってくることだけを知っていればよいのです。

## 概要と基本機能

API Gatewayは、AWSが提供するマネージドサービスです。
バージョン管理、環境ごとのデプロイ、認証・認可、モニタリングなどを、一元管理できます。

| 特徴 | 説明 |
| --- | --- |
| スケーラブル | 自動でトラフィックに対応します。 |
| プロトコル対応 | REST API、HTTP API、WebSocket APIをサポートします。 |
| セキュリティ | 認証、アクセス制御、リクエスト制限ができます。 |
| 開発効率化 | 簡単な設定で、バックエンドと連携できます。 |

| 役割 | 説明 |
| --- | --- |
| クライアントとバックエンドの仲介 | リクエストとレスポンスを処理します。 |
| リクエストの認証と認可 | IAM、Cognito、カスタムオーソライザーで管理します。 |
| データ変換 | JSONからXMLなど、フォーマットを変換します。 |
| キャッシュ | 頻繁にアクセスされるデータをキャッシュして、レスポンスを速くします。 |

:::message
**マネージドサービスとは**: AWSがインフラの管理を行ってくれるサービスです。サーバー、ストレージ、ネットワーク機器のセットアップ、運用、障害対応を任せられます。
:::

## ユースケース

| 種類 | 説明 | 例 | 連携先 |
| --- | --- | --- | --- |
| REST API | フロントやモバイルアプリが、データを取得するエンドポイントとして使います。 | DynamoDBやRDSのデータを返します。 | EC2、ECS、DynamoDB、RDS、S3など |
| WebSocket | 双方向通信が必要な、リアルタイムアプリで使います。 | チャットアプリ、通知システム | Lambda、IoT Coreなど |
| Lambda統合 | サーバーレスのフロントとして使います。 | Lambdaで処理して、結果を返します。 | Lambda、Step Functionsなど |

## REST APIとHTTP APIの違い

どちらも、基本的にはHTTPプロトコルを使いますが、仕様にいくつか違いがあります。

* **REST API**: 高機能ですが、レイテンシーは高めです。認証やリクエストパスの設定が必要です。
* **HTTP API**: 軽量版で、低レイテンシーで、設定が簡単です。多くの場合、REST APIよりシンプルです。

| 特徴 | REST API | HTTP API |
| --- | --- | --- |
| パフォーマンス | 高機能だがレイテンシーは高め | 軽量で低レイテンシー |
| 認証 | APIキー、IAM認証が主流 | JWT認証が一般的 |
| コスト | HTTP APIより高い | REST APIより低い |
| ユースケース | 高度な機能が必要な場合 | シンプルなユースケース |

呼び出し側のコードは、どちらも次のようになります。

```js
const axios = require('axios');

const apiUrl = "https://example.execute-api.us-east-1.amazonaws.com/resource";
const token = "your-auth-token"; // 必要に応じてJWTなどの認証トークンを使用

async function callApi() {
  try {
    const response = await axios.post(
      apiUrl,
      { data: "Sample payload" }, // リクエストボディ
      { headers: { Authorization: `Bearer ${token}` } }
    );
    console.log("API Response:", response.data);
  } catch (error) {
    console.error("Error calling API:", error.response ? error.response.data : error.message);
  }
}

callApi();
```

そのほかにも違いがあるので、一度ドキュメントに目を通すのがおすすめです。

* [HTTP API と REST API の間で選択する](https://docs.aws.amazon.com/ja_jp/apigateway/latest/developerguide/http-api-vs-rest.html)

## 知っておくと幸せになれること

### パフォーマンスの最適化

| 最適化方法 | 説明 | 設定例 |
| --- | --- | --- |
| キャッシュ | レスポンスをキャッシュして、同じリクエストへのバックエンド呼び出しを避けます。レイテンシーと負荷を減らせます。 | ステージ設定でキャッシュを有効化、TTLを300秒に設定、キャッシュキーにクエリ文字列を追加 |
| スロットリング | リクエスト数を制限して、過剰なトラフィックやDDoS攻撃を防ぎます。 | 最大リクエスト数100/秒、バーストキャパシティ200、ユーザーごとにAPIキーで制限 |
| ペイロード | リクエストやレスポンスのサイズを減らして、処理を速くします。 | gzip圧縮を有効化、レスポンスを最小限にする、必要なフィールドだけ返す |

### VPCのリソースにアクセスさせるには

VPC内のリソースとAPI Gatewayをつなぐには、**VPCリンク**というリソースを作ります。
これで、API GatewayがVPC内のリソースに、安全にアクセスできます。

### 認証・認可はAPI Gatewayでやる？

バックエンドにWebフレームワークを使うなら、フレームワークで認証・認可をすればよい、と思っていました。
ですが、調べていくと、API Gatewayで行うほうが効率的な場面が多いと分かりました。
また、**API Gatewayでの認証・認可と、Webフレームワークでの認証・認可の2段階**にすると、セキュリティの強化にもつながると考えています。(冗長ですが、重ねて対策することが大切です。)

| 目的 | 詳細 | メリット |
| --- | --- | --- |
| 不要なトラフィックの遮断 | 認証に失敗したリクエストを、バックエンドに渡す前に遮断します。 | 不正リクエストによる、バックエンドのリソース消費を減らせます。 |
| セキュリティ強化 | OAuth 2.0、Cognito連携、IAMポリシーなど、高度な設定ができます。 | AWSのセキュリティ機能を活用して、バックエンドの脆弱性の露出を減らせます。 |
| スケーラビリティの向上 | スロットリングやIP制限で、トラフィックを管理します。 | 突発的なアクセス増加に対応して、バックエンドの負荷を減らせます。 |
| 認証ロジックの共通化 | 複数のバックエンドやマイクロサービスで、認証を統一します。 | 各バックエンドで、認証を実装する必要がなくなります。 |
| AWSリソースとの連携 | IAM認証や、S3、DynamoDBなどとの連携が簡単です。 | AWSサービスへ、安全にアクセスできます。 |
| バックエンドのシンプル化 | 認証処理をAPI Gatewayで行って、バックエンドはビジネスロジックに集中します。 | コードがシンプルになり、保守性が向上します。 |

## まとめ

* API Gatewayは、認証・認可、キャッシュ、スロットリングなどを備えた、マネージドな玄関口です。
* REST APIは高機能、HTTP APIは軽量・低コストです。用途で選びましょう。
* VPC内のリソースには、VPCリンクで接続します。
* 認証・認可は、API Gatewayとアプリの両方で行うと、さらに安全です。
