クラウドメタデータ攻撃の仕組みと、Nginxでの対策をまとめました。
AWSなどのクラウド上で、Nginxを使ってWebサーバーを運用している方に向けた内容です。

## 結論

NginxのHostヘッダーが `169.254.169.254` のリクエストを、`403` で拒否する設定を入れましょう。
あわせて、EC2のメタデータサービスは、IMDSv2(トークン必須)にしておくと、より安全です。

## クラウドメタデータとは

クラウド環境でサーバー(インスタンス)を動かすと、「メタデータ」というものがあります。
これは、そのサーバー自身の「身分証明書」のような情報で、次のようなものが含まれます。

* **インスタンスID**: そのサーバー固有の識別番号
* **ロール・認証情報**: ほかのクラウドサービスにアクセスするための権限や秘密鍵など
* **ネットワーク情報**: サーバーのIPアドレスなど
* **起動スクリプト**: サーバーが起動時に実行するコマンド

これらの情報は、サーバーが自分自身を識別したり、ほかのクラウドサービスと安全に連携したりするために重要です。
メタデータには、通常、`169.254.169.254` という特別なIPアドレスを通じて、**サーバー内部からだけ**アクセスできます。

### 169.254.169.254ってどんなIP？

`169.254.169.254` は、「**リンクローカルアドレス**」と呼ばれる、特殊な範囲のIPアドレスです。
インターネットのような外部ネットワークからはアクセスできず、サーバー自身の内部ネットワークでだけ有効です。
そのため、通常は、サーバー内部のアプリケーションだけが、自分の情報を取得するために使います。

## クラウドメタデータ攻撃の仕組み

この攻撃は、本来アクセスできないはずのメタデータに、**不適切な設定を悪用して**アクセスしようとするものです。
狙われるのが、Webサーバーとしてよく使われる**Nginx**の設定ミスです。

メタデータを取得するコマンドの例です。

```bash
curl -H "X-aws-ec2-metadata-token: $(curl -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")" http://169.254.169.254/latest/meta-data/
```

### 攻撃の手順

1. **Nginxの誤設定**: Nginxが、特定のルールなしに、外部からのリクエストを内部のIPアドレスに転送してしまう、不適切な設定になっていることが前提です。
2. **特別なリクエストの送信**: 攻撃者は、悪意のあるHTTPリクエストをNginxに送ります。このとき、**Hostヘッダー**に `169.254.169.254` を意図的に含めます。
3. **Nginxの転送**: 誤設定されたNginxが、Hostヘッダーに `169.254.169.254` を含むリクエストを、内部のメタデータサービスに転送してしまいます。
4. **メタデータの取得**: 結果として、外部の攻撃者が、サーバーの機密性の高いメタデータ(認証情報など)を、不正に取得できてしまいます。

攻撃が成功すると、攻撃者はサーバーになりすまして、ほかのクラウドサービスにアクセスしたり、機密情報を盗んだりします。深刻な被害につながるおそれがあります。

## Nginxで防ぐ方法

最も効果的で直接的な方法は、**Nginxの設定を正しく行う**ことです。
Nginxの設定ファイル(`/etc/nginx/nginx.conf` や `/etc/nginx/conf.d/` のサイト設定)に、次のルールを追加します。

```nginx
server {
    listen 80;
    listen 443 ssl; # HTTPSを使用している場合
    server_name your-domain.com; # 実際のドメイン名に置き換える

    location / {
        # HostヘッダーがメタデータIPアドレス(169.254.169.254)の場合、
        # アクセスを拒否して、403 Forbiddenを返す
        if ($http_host = "169.254.169.254") {
            return 403;
        }
    }

    # その他のNginx設定
    # ...
}
```

### 設定のポイント

* `if ($http_host = "169.254.169.254")`: 核心の部分です。受け取ったリクエストの `Host` ヘッダーが `169.254.169.254` かどうかをチェックします。
* `return 403;`: 一致したら、リクエストを処理せずに、すぐ `403 Forbidden` を返します。これで、攻撃者がメタデータにアクセスするのを防ぎます。

設定を追加したら、必ずテストして、再読み込みします。

```bash
sudo nginx -t                 # 設定ファイルの文法チェック
sudo systemctl reload nginx   # Nginxの設定を再読み込み
```

## 合わせてやっておきたい対策

:::message
EC2の場合は、メタデータサービスを**IMDSv2**(セッショントークン必須)に設定しておくと、この種の攻撃(SSRFなど)の被害を抑えられます。
Nginxの設定とあわせて、多層で防御しましょう。
:::

## まとめ

* クラウドメタデータには、認証情報などの機密情報が含まれます。
* Nginxの誤設定があると、外部から `169.254.169.254` のメタデータに到達されるおそれがあります。
* Hostヘッダーが `169.254.169.254` のリクエストを `403` で拒否しましょう。
* IMDSv2の有効化など、多層での防御もあわせて行いましょう。
