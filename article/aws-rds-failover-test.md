RDS for MySQLで、フェイルオーバーを実際に試した検証内容をまとめました。
DBの冗長構成を検討している方や、フェイルオーバー時の挙動を知りたい方に向けた内容です。

## 結論

* フェイルオーバー中はデータの登録が途切れますが、DBが復旧すれば、登録を再開できます。
* エンドポイントが変わらないので、プログラム側で特別な処理は不要です。
* ただし、PHP側にタイムアウトの設定を入れないと、復旧後も処理が続かないことがありました。

## DBの冗長構成とは

冗長構成とは、簡単に言うと、**システムに障害が起きたときに、自動で別のバックアップシステムやリソースに切り替えて、中断を最小限に抑える仕組み**です。

冗長構成を取っておくと、DBに障害が起きても、被害を最小限に抑えて運用を続けられます。
データが壊れると、案件によっては損害賠償に発展したり、ユーザーに悪影響が出たりして、ビジネスチャンスを失います。
できるだけ冗長構成を取りましょう。

## 検証の準備

:::message alert
RDSには、ちゃんとお金がかかります。自分で払える範囲のスペックで構築してください。
検証が終わったら、RDSは削除してください。
RDSは、停止していてもお金がかかります(インスタンス料金、データベースストレージ料金、バックアップストレージ料金)。
:::

EC2とRDS(マルチAZ)の構築は済ませておきます。
そのうえで、1秒ごとにDBへデータを登録する処理を、PHPで書きます。

```php
<?php
ini_set('mysqlnd.net_read_timeout', 3);

$i = 0;
$end_time = time() + 600;

while (time() < $end_time) {
    $result = hoge();
    sleep(1);
    echo $i . ":" . $result . "\n";
    $i++;
}

function hoge() {
    $result = 'connectionWaiting';
    try {
        $dbh = new PDO(
            'mysql:host=<RDSのエンドポイント>;dbname=testDB;charset=UTF8mb4',
            'admin',
            'password'
        );
        $dbh->setAttribute(PDO::ATTR_TIMEOUT, 3);

        $sql = "INSERT INTO testTable (created) VALUES ('" . date('Y-m-d H:i:s') . "')";
        if ($dbh->query($sql)) {
            $result = 'Success';
        } else {
            $result = 'Fail';
        }
    } catch (PDOException $e) {
        $result = 'Die';
    }
    return $result;
}
```

## 実行する

### PHPを実行する

```bash
php index.php
```

### RDSをフェイルオーバーで再起動する

RDSは、フェイルオーバーを伴う再起動ができます。
データ登録のPHPを実行している状態で、フェイルオーバーのオプションを付けて、再起動します。

フェイルオーバー実行前のデータです。

```
mysql> select * from testTable;
+----+---------------------+
| id | created             |
+----+---------------------+
|  1 | 2023-10-18 10:39:07 |
|  2 | 2023-10-18 10:39:08 |
|  3 | 2023-10-18 10:39:09 |
|  4 | 2023-10-18 10:39:10 |
|  5 | 2023-10-18 10:39:11 |
|  6 | 2023-10-18 10:39:12 |
+----+---------------------+
```

フェイルオーバー実行後のデータです。

```
mysql> select * from testTable;
+----+---------------------+
| id | created             |
+----+---------------------+
| 56 | 2023-10-18 10:40:03 |
| 57 | 2023-10-18 10:40:04 |  ← 再起動で止まったところと思われる箇所
| 58 | 2023-10-18 10:41:10 |  ← 再起動が完了したところと思われる箇所
| 59 | 2023-10-18 10:41:11 |
| 60 | 2023-10-18 10:41:12 |
+----+---------------------+
```

10:40:04 から 10:41:10 までの、約1分間、データが途切れています。

## わかったこと

* データは途切れるが、DBの復旧とともに、登録を再開できます。
  * 被害が大きくなりにくいです。
  * エンドポイントが変わらないので、プログラム側で特別な処理は不要です。(これがとても嬉しいです。)
* 難しい設定は不要です。
  * 自分でMySQLの高可用性構成を作る方法は、Oracleが解説しています。
    * https://www.oracle.com/jp/a/tech/docs/technical-resources/120127-mysql-ha.pdf
    * https://downloads.mysql.com/presentations/01_201311_MySQL_JP_Tech-Tour.pdf

## わかっていないこと

* **大量のデータになった場合の復旧時間**
  * 今回の検証でも、すぐ終わるときもあれば、3分以上かかるときもありました。
* **PHP側のタイムアウト設定**
  * `ini_set('mysqlnd.net_read_timeout', 3)` を入れないと、再起動が完了しても、処理が継続しませんでした。
  * RDS側でデッドロックが起きているのか、接続先を探しているのか、RDS側の設定が必要なのかは、分かっていません。
  * とりあえず、プログラムで、ちょっとした工夫は必要そうです。

## まとめ

* RDSのマルチAZで、フェイルオーバーによる冗長性を確保できました。
* フェイルオーバー中は、1〜3分ほどデータの登録が途切れる可能性があります。
* アプリ側にも、タイムアウトの設定などの工夫が必要です。
* DBを使わないシステムはほとんどないので、「DBが死んでも大丈夫」な構成でビジネスチャンスを失わないことが大切だと考えています。
