「なんとなく」で出していたログをやめて、トラブルシューティングや分析に役立つログを設計するために学んだことをまとめました。
障害対応で、ログが役に立たなかった経験のある方に向けた内容です。

## 結論

* ログは、「読むもの」ではなく「検索・集計するもの」として、**構造化ログ(JSON)**で出力します。
* 1リクエストごとに**Trace ID**を付けて、全ログに含めます。
* 機密情報は出さず、握りつぶしのログも書きません。

## はじめに

正直に告白すると、これまでは、なんとなくログを出していました。
「エラーが起きたら怖いから、とりあえず `try-catch` してログに残しておこう」「ないよりはマシだろう」という感じです。

でも、いざ本番で障害が起きたとき、そのログは助けになりませんでした。
深夜のアラート対応で、「システムエラーが発生しました」とだけ書かれたログを前に、途方に暮れた経験はありませんか？

## ログの目的を再定義する

ログを書く目的は、次の3つです。

1. **トラブルシューティング**(Why & Where?)
   * 「なぜ落ちたのか」「どこで落ちたのか」を特定して、バグを再現・修正するためです。
2. **可観測性・分析**(Observability)
   * 「この機能はどれくらい使われているか」「処理に何秒かかっているか」など、システムの状態やユーザーの行動を知るためです。
3. **監査・セキュリティ**(Security)
   * 「いつ、誰が、重要なデータを変更したか」の証跡を残すためです。

これらを意識すると、「とりあえず出力」ではなく、**「目的に合わせて出力」**する必要があると気づきます。

## 構造化ログとは

構造化ログとは、**ログを人間への手紙ではなく、機械へのデータとして扱う**ことです。

### 非構造化ログ

従来のテキスト形式のログです。

```php
// 人間には読めるが、機械(検索)には辛い
Log::error("User 123 failed to login from 192.168.0.1");
```

これだと、「ユーザーID 123 のエラーだけ集計したい」ときに、正規表現で文字列を解析する必要があります。
ログの文言が少し変わっただけで、検索できなくなってしまい、運用がとてもつらくなります。

### 構造化ログ

ログをJSONなどの形式で出力します。

```php
// メッセージとデータを分ける
Log::error("Login failed", [
    "user_id" => 123,
    "ip_address" => "192.168.0.1",
    "event" => "auth_error"
]);
```

出力されるJSONは、こうなります。

```json
{
  "level": "ERROR",
  "message": "Login failed",
  "context": {
    "user_id": 123,
    "ip_address": "192.168.0.1",
    "event": "auth_error"
  },
  "datetime": "2024-01-07T12:00:00+09:00"
}
```

DatadogやCloudWatch Logsなどのログ管理ツールで、`context.user_id = 123` のようにクエリ一発で検索・集計できます。
現代のWeb開発では、**ログは「読むもの」ではなく、「検索・集計するもの」**です。構造化ログは必須と言えます。

## ログ設計の実践

### やるべきこと

**コンテキスト(文脈)を含める**

「エラーです」だけでは意味がありません。
「そのとき何が起きていたか」を、連想配列(Context)として渡しましょう。5W1Hを意識するといいと思います。

* 誰が?(User ID)
* 何を?(Input Data)
* どこで?(Request URL、IP Address)

**Trace ID(Request ID)を通す**

今回、一番の学びでした。
「1回のリクエスト」にユニークなID(Trace ID)を割り当てて、すべてのログに含めます。

```json
{
    "message": "DB error",
    "request_id": "a0eebc99-9c0b...",
    "user_id": 101
}
```

これがあれば、マイクロサービスや非同期処理でログがバラバラになっても、**IDで検索して、一連の処理の流れを追えます。**

Laravelなら、ミドルウェアでIDを自動で発行して、`Log::shareContext()` などですべてのログに自動で付与しておくと、コードを書くときに意識しなくて済むので最高です。

**ログレベルを使い分ける**

チーム内の基準に従いましょう。ない場合は、基準を決めておきましょう。次は一例です。

* **ERROR**: 即時対応が必要です(深夜でも電話がかかってくるレベルです)。
* **WARN**: 異常ですが、システムは稼働を続けられます(あとで確認します)。
* **INFO**: 正常系のイベントです(KPI分析や動作確認用です)。
* **DEBUG**: 開発時のデバッグ用です(本番では出しません)。

### アンチパターン

**機密情報を出力する**

パスワード、アクセストークン、クレジットカード番号、個人情報(PII)は、ログに出してはいけません。
ログファイル自体が漏洩したときのリスクが大きく、しかも平文です。

**「とりあえずcatchしてログ」で握りつぶす**

一番やりがちなパターンです。

```php
try {
    $user->save();
} catch (Exception $e) {
    // 最悪なパターン: エラーが起きた事実だけログして、処理を続行してしまう
    Log::error("Error happened");
}
```

これだと、データ不整合が起きているのにシステムが動き続けて、あとで原因不明のバグになります。
対処できないエラーは、ログに出すだけでなく、**例外を再スローするか、エラーレスポンスを返す**必要があります。

## ログ運用

### 出力先は標準出力

DockerやKubernetesなどのコンテナ環境では、**標準出力(stdout/stderr)に出す**のが定石です。([The Twelve-Factor App](https://12factor.net/ja/logs)の考え方です。)

アプリは、標準出力にJSONを流すだけにします。
あとは、FluentdやDatadog Agentがそれを拾って、S3やログ管理基盤に転送します。
アプリが「ログの保存場所」を知らなくていい設計が、モダンな運用です。

### ログローテート

最後に、地味だけど大事な話です。
ファイルにログを出力する場合、書き続けると、いつかディスクが溢れます。
数GBのテキストファイルを開こうとして、エディタが固まった経験もあると思います。
(以前対応したEC2のアラートでは、15GBのログファイルがサーバーを圧迫していたことがありました。)

* **ローテート**: 日次やサイズ指定で、ファイルを分割します(例: `app.log` → `app.log.2024-01-07`)。
* **保持期間**: 「14日経過したら削除する」などのルールを決めます。

PHP(Monolog)なら、`RotatingFileHandler` で簡単に実装できます。Linuxの `logrotate` で管理することもあります。
「ディスクフルでサーバーダウン」は一番悲しい障害なので、リリース前に必ず確認しましょう。

## まとめ

* ログの目的は、トラブルシューティング、可観測性・分析、監査・セキュリティの3つです。
* 構造化ログ(JSON)にして、コンテキストとTrace IDを含めましょう。
* 機密情報の出力と、`catch` してログだけ出す握りつぶしは避けます。
* コンテナ環境では標準出力に出して、ファイル出力ならローテートと保持期間を決めておきます。

ログ設計の見直しは、未来の自分やチームメイトへの思いやりです。
「何かあったとき、このログを見て原因が分かるか?」「1年後の自分が、このログを見て感謝するか?」と自問しながら、`Log::info()` を書いていきましょう。
